# Liventra — Business Logic Documentation
## Model 08: FeedRecommendation

**Document Version:** Business Logic v1.0  
**Project:** Liventra — Smart Livestock Farm Management System  
**Database:** MongoDB  
**Architecture:** MERN

---

# 1. Source / Finalized Model

The FeedRecommendation model finalized for Liventra is:

```text
_id
farmId
animalId
formulaId (optional)

generatedAt

inputSnapshot:
    age
    currentWeight
    stage
    purpose
    pregnancyStatus
    lactationStatus
    milkYield
    targetADG
    season

recommendedItems:
    [
        {
            ingredientId
            ingredientName
            quantity
            unit
            estimatedCost
        }
    ]

totalRecommendedDMI
estimatedDailyCost

explanation[]
warnings[]

ruleVersion

status:
    draft
    confirmed
    expert_approved
    rejected
    superseded

reviewedBy
reviewedAt

createdBy
createdAt
updatedAt
```

The important design decision discussed for Liventra is that a preview recommendation does **not** need to be permanently saved. Once the user confirms it, or once it becomes an official generated recommendation, it is saved as a historical record.

When a recommendation changes, the old record should **not be overwritten**. A new recommendation record should be created.

`expert_approved`, `reviewedBy`, and `reviewedAt` remain optional for the current implementation.

---

# 2. Purpose

`FeedRecommendation` represents the **animal-specific feeding recommendation generated by Liventra at a particular point in time**.

This is different from FeedFormula.

### FeedIngredient

```text
What is this ingredient?
```

### FeedFormula

```text
What is the approved/general feeding formula
for a defined condition?
```

### FeedRecommendation

```text
What should THIS animal receive based on
its condition at THIS point in time?
```

### FeedRecord

```text
What was ACTUALLY fed?
```

Therefore:

```text
FeedIngredient
      ↓
FeedFormula
      ↓
FeedRecommendation
      ↓
FeedRecord
```

---

# 3. Why FeedRecommendation Is Necessary

Suppose today:

```text
Animal A
Weight = 180 kg
Stage = Growing
Target ADG = 0.8 kg/day
Season = Summer
```

The system generates:

```text
Napier Grass = 12 kg
Concentrate = 3 kg

Estimated Cost = ৳280/day
```

Two months later:

```text
Weight = 230 kg
```

and the feeding rules have changed.

The new recommendation may become:

```text
Napier Grass = X kg
Concentrate = Y kg
```

If the system simply recalculates the old recommendation from the current Animal document, then the original 180 kg recommendation disappears conceptually.

That creates serious problems for:

- Thesis evaluation
- Expert validation
- Farmer history
- Auditability
- Recommendation comparison
- Model/rule evaluation

Therefore, FeedRecommendation is designed as a **historical snapshot record**.

---

# 4. Core Principle — Recommendation Is a Snapshot

This is the most important business rule.

At generation time, Liventra captures:

```text
Animal Context
      +
Formula/Rule Context
      +
Recommendation Output
```

and stores them.

Conceptually:

```text
                 At Time T1

Animal:
Weight = 180 kg
Stage = Growing
Season = Summer
Target ADG = 0.8

          ↓

Recommendation R1

          ↓

Snapshot saved
```

Later:

```text
                 At Time T2

Animal:
Weight = 230 kg
Stage = Growing
Season = Summer
Target ADG = 0.8

          ↓

Recommendation R2

          ↓

New snapshot saved
```

R1 must remain unchanged.

---

# 5. Historical Immutability

Once a recommendation becomes an official saved recommendation:

```text
R1
```

should be treated as historical evidence.

Do **not** update R1 because:

```text
Animal weight changed
Milk yield changed
Season changed
Feed price changed
Formula changed
Ingredient nutrition changed
Rule version changed
```

Instead:

```text
R1 → historical recommendation

R2 → new recommendation
```

This is central to the project's recommendation architecture.

# 6. Field-by-Field Business Logic

# 6.1 `_id`

### Type

MongoDB `ObjectId`

### Required

Yes

### Purpose

Unique identifier for the recommendation record.

Example:

```text
REC-000001
```

The actual MongoDB `_id` remains the internal database identifier.

---

# 6.2 `farmId`

### Type

ObjectId / Farm reference

### Required

Yes

### Purpose

Identifies the farm for which the recommendation was generated.

### Business Logic

Every recommendation must belong to a farm.

This is important for:

- Multi-farm isolation
- Authorization
- Farm dashboards
- Reporting
- Audit
- Cost analysis

---

# 6.3 `animalId`

### Type

ObjectId / Animal reference

### Required

Yes

### Purpose

Identifies the specific animal receiving the recommendation.

Relationship:

```text
Farm
  ↓
Animal
  ↓
FeedRecommendation
```

Many recommendations can belong to one animal over time.

```text
Animal A
   |
   +--- R1
   +--- R2
   +--- R3
   +--- R4
```

---

# 6.4 `formulaId`

### Type

ObjectId / FeedFormula reference

### Required

Optional

### Purpose

Identifies the FeedFormula used as the source/base for the recommendation.

Example:

```text
formulaId → FF-000010
```

### Why Optional?

Not every future recommendation mechanism must necessarily be generated from one stored FeedFormula.

For example, a future rule engine or expert-created recommendation may produce a recommendation without selecting a predefined formula.

Therefore:

```text
formulaId = null
```

can be valid.

### Important

If a formula was used, storing `formulaId` provides traceability.

---

# 7. `generatedAt`

### Type

Date

### Required

Yes

### Purpose

Records the exact time the recommendation was officially generated/saved.

Example:

```text
2026-08-17T10:30:00
```

### Business Uses

- Historical timeline
- Recommendation comparison
- Audit
- Research evaluation
- Rule-version analysis

---

# 8. `inputSnapshot`

This is the heart of the historical recommendation design.

It stores the animal/context values that were used when the recommendation was generated.

Structure:

```text
inputSnapshot:
    age
    currentWeight
    stage
    purpose
    pregnancyStatus
    lactationStatus
    milkYield
    targetADG
    season
```

---

# 9. Why inputSnapshot Is Necessary

Without the snapshot, the system might store only:

```text
animalId
formulaId
generatedAt
```

Then later someone asks:

> "What information did the system use when it generated this recommendation?"

The current Animal document might have completely different values.

Example:

```text
At generation:
Weight = 180 kg
```

Current:

```text
Weight = 230 kg
```

If only `animalId` is stored, the historical context is lost.

With snapshot:

```text
inputSnapshot.currentWeight = 180
```

the historical context remains available.

---

# 10. `inputSnapshot.age`

### Type

Number / age representation

### Required

Yes/according to recommendation input availability

### Example

```text
2.5 years
```

### Purpose

Stores the animal's age at recommendation-generation time.

### Critical Rule

Do not depend on the current Animal birthDate alone when displaying an old recommendation.

The snapshot preserves the historical age used at that time.

---

# 11. `inputSnapshot.currentWeight`

### Type

Number

### Unit

kg

### Example

```text
180
```

### Purpose

Stores the animal's weight at recommendation-generation time.

### Example

```text
R1:
currentWeight = 180 kg

R2:
currentWeight = 230 kg
```

This allows Liventra to compare how recommendations changed as the animal grew.

---

# 12. `inputSnapshot.stage`

### Type

Enum/string representation

### Example

```text
Growing
```

### Purpose

Stores the stage used during recommendation generation.

Possible values align with the FeedFormula stage classification:

```text
Calf
Growing
Heifer
Lactating
Dry
Breeding
```

### Why Snapshot?

The animal's stage may change later.

The recommendation must preserve the stage used at generation time.

---

# 13. `inputSnapshot.purpose`

### Type

Enum/string representation

### Example

```text
Growth
```

### Purpose

Stores the feeding objective used during recommendation generation.

Possible values align with FeedFormula purpose:

```text
Maintenance
Breeding
Growth
Milk Production
```

---

# 14. `inputSnapshot.pregnancyStatus`

### Type

Boolean/status representation

### Example

```text
true
```

### Purpose

Captures whether pregnancy status was considered in the recommendation.

### Business Logic

Pregnancy can change nutritional requirements.

Therefore, if pregnancy influenced the recommendation, that information must remain part of the snapshot.

---

# 15. `inputSnapshot.lactationStatus`

### Type

Boolean/status representation

### Example

```text
true
```

### Purpose

Captures whether the animal was lactating at recommendation-generation time.

### Business Logic

Lactation can strongly influence feed requirements.

Historical recommendation records must preserve whether lactation was active at the time.

---

# 16. `inputSnapshot.milkYield`

### Type

Number

### Unit

Normally:

```text
Liter/day
```

### Example

```text
18
```

### Purpose

Stores the milk yield used as recommendation input.

### Important

This is a snapshot, not a replacement for MilkRecord.

```text
MilkRecord
    ↓
Historical production

FeedRecommendation.inputSnapshot.milkYield
    ↓
Value used for this specific recommendation
```

---

# 17. `inputSnapshot.targetADG`

### Type

Number

### Unit

kg/day

### Example

```text
0.8
```

### Meaning

Target Average Daily Gain.

### Business Use

Particularly important for:

```text
Growing
Growth
Beef
```

recommendations.

---

# 18. `inputSnapshot.season`

### Type

Enum/string representation

### Example

```text
Summer
```

### Purpose

Stores the season used by the recommendation engine.

Possible values align with FeedFormula:

```text
Summer
Winter
Rainy
All Season
```

### Why Snapshot?

Season changes over time.

A historical recommendation should always show the season under which it was generated.

# 19. Recommended Items

Structure:

```text
recommendedItems:
[

        ingredientId
        ingredientName

        estimatedCost

```

This is the actual output of the recommendation engine.

---

# 20. `recommendedItems[].ingredientId`

### Type

ObjectId / FeedIngredient reference

### Required

Yes

### Purpose

Identifies which ingredient was recommended.

Example:

```text
ingredientId → Napier Grass
```

### Business Logic

Allows the system to connect the recommendation to:

- Ingredient master data
- Inventory
- FeedRecord
- Formula
- Cost

---

# 21. `recommendedItems[].ingredientName`

### Type

String

### Required

Yes

### Example

```text
Napier Grass
```

### Why Store Both ID and Name?

`ingredientId` provides relational/reference identity.

`ingredientName` acts as a human-readable snapshot.

Example:

```text
At T1:
ingredientName = "Rice Bran"
```

Later the master name could be changed.

The historical recommendation should still show what was displayed when it was generated.

This is a deliberate denormalization for historical traceability.

---

# 22. `recommendedItems[].quantity`

### Type

Number

### Required

Yes

### Example

```text
12
```

### Meaning

Recommended quantity of the ingredient.

---

# 23. `recommendedItems[].unit`

### Type

String/enum aligned with ingredient unit

### Example

```text
kg
```

### Purpose

Defines how the recommended quantity should be interpreted.

Example:

```text
12 kg
```

---

# 24. `recommendedItems[].estimatedCost`

### Type

Number

### Required

Yes/according to implementation

### Example

```text
60
```

### Unit

BDT.

### Meaning

Estimated cost of that recommended ingredient quantity at recommendation time.

Conceptually:

```text
Recommended quantity
       ×
Applicable price
       =
Estimated ingredient cost
```

---

# 25. Why Estimated Cost Is Stored in Recommendation

Suppose:

```text
Today:
Napier = ৳5/kg

Recommendation:
12 kg
Estimated cost = ৳60
```

Next month:

```text
Napier = ৳7/kg
```

If the recommendation dynamically recalculated from current price, the old recommendation would show:

```text
৳84
```

instead of:

```text
৳60
```

That would destroy historical accuracy.

Therefore the recommendation stores its own cost snapshot.

---

# 26. `totalRecommendedDMI`

### Type

Number

### Required

Yes/according to recommendation type

### Meaning

Total Recommended Dry Matter Intake.

### Purpose

Provides the total recommended dry matter quantity for the animal.

### Business Use

Useful for:

- Nutrition analysis
- DMI comparison
- Feed efficiency
- Recommendation validation
- Research evaluation

### Important

DMI should not be confused with total as-fed feed quantity.

For example:

```text
As-fed feed = 20 kg

Dry matter = 5 kg
```

can be conceptually possible depending on feed moisture.

The exact calculation must follow the project's approved nutritional methodology.

---

# 27. `estimatedDailyCost`

### Type

Number

### Required

Yes

### Unit

BDT/day

### Example

```text
280
```

### Purpose

Total estimated daily feeding cost of the recommendation.

Conceptually:

```text
Ingredient 1 estimated cost
+
Ingredient 2 estimated cost
+
Ingredient 3 estimated cost
...
=
estimatedDailyCost
```

# 28. `explanation[]`

Array of Strings

### Required

# 29. Why Explanation Is Important

A farmer may ask:

> "Why did the system recommend this amount?"

Instead of only showing:

```text
Napier = 12 kg
Concentrate = 3 kg
```

Liventra can show:

```text
Animal weight = 180 kg
Stage = Growing
Target ADG = 0.8 kg/day
Season = Summer
```

and explain the recommendation.

This improves:

- Transparency
- Farmer trust
- Expert review
- Thesis explainability

Array of Strings

### Required

# 33. `status`

### Type

Enum

### Allowed Values

```text
draft
confirmed
expert_approved
rejected
superseded
```

### Purpose

Controls the lifecycle of the recommendation.

---

# 34. Status — `draft`

Meaning:

```text
Recommendation generated/prepared
but not yet officially confirmed.
```

A draft can be reviewed or edited according to the application workflow.

### Important

A temporary preview does not necessarily need to be stored as a draft.

The project decision is:

> Preview recommendations do not need to be persisted until the user confirms them or the recommendation becomes officially generated.

---

# 35. Status — `confirmed`

Meaning:

```text
User/farm operator accepted the recommendation.
```

Example:

```text
System generated
      ↓
Farmer reviews
      ↓
Confirm
      ↓
status = confirmed
```

This is an important point at which the recommendation becomes an official historical record.

---

# 36. Status — `expert_approved`

Meaning:

```text
An authorized expert has reviewed and approved it.
```

### Current Project Decision

This is optional for now.

Therefore:

```text
reviewedBy = optional
reviewedAt = optional
```

The project can enable expert review later.

---

# 37. Status — `rejected`

Meaning:

```text
Recommendation was reviewed and rejected.
```

Reasons can be preserved through:

```text
warnings[]
explanation[]
```

or the application's review mechanism.

A rejected recommendation should remain in history rather than being deleted if it was officially generated/reviewed.

---

# 38. Status — `superseded`

Meaning:

```text
A newer recommendation has replaced this recommendation
for the same animal/context.
```

Example:

```text
R1
Weight = 180 kg
Status = superseded

      ↓

R2
Weight = 230 kg
Status = confirmed
```

### Important

Superseded does NOT mean deleted.

It means:

```text
No longer the latest recommendation
```

while preserving history.

---

# 39. Status Transition Logic

A reasonable lifecycle is:

```text
draft
  ↓
confirmed
  ↓
superseded
```

or:

```text
draft
  ↓
rejected
```

Optional expert workflow:

```text
confirmed
  ↓
expert_approved
```

The exact transition permissions should be enforced in the service layer.

### Type

Date

### Required

Yes

The presence of `updatedAt` does NOT mean the recommendation's historical contents should be freely overwritten.

```text
          ↓

          ↓

          ↓

          ↓

          ↓
```

# 46. Preview vs Official Recommendation

This is an explicit project decision.

## Preview

```text
System calculates
      ↓
User sees result
```

No database record is required.

## Confirmed / Official

```text
User confirms
      ↓
Create FeedRecommendation document
```

This avoids filling the database with temporary calculations.

---

# 47. Recommendation Update Principle

Suppose an existing recommendation is:

```text
R1
```

and the user requests a new recommendation because:

```text
weight changed
milk yield changed
season changed
rule changed
```

Do NOT do:

```text
UPDATE R1
```

Instead:

```text
Create R2
```

Then:

```text
R1.status = superseded
R2.status = confirmed
```

This preserves history.

```text
F2
```

# 55. What If Ingredient Price Changes?

Suppose:

```text
At R1:
Napier = ৳5/kg
```

R1 stores:

```text

```

```text
Napier = ৳7/kg
```


# 56. What If Ingredient Nutrition Changes?

Suppose:

```text

```

is updated later.

The old recommendation must not silently recalculate.

Historical:

```text
R1
```

remains unchanged.

Future:

```text
R2
```

uses the new approved nutrition/rule data.

# 57. Recommendation Explanation Logic

Explanation should be generated from the actual decision inputs.

Example:

```text
Animal weight: 180 kg
Stage: Growing
Target ADG: 0.8 kg/day
Season: Summer
```

Possible explanation:

```text
"Recommendation was selected for a growing animal
weighing 180 kg with a target ADG of 0.8 kg/day
under summer conditions."
```

The explanation should describe the actual logic used rather than generic text.

---

# 58. Warning Logic

Warnings may be generated when:

```text
No exact formula match
Missing milk data
Missing weight data
Ingredient unavailable
Animal under treatment
Animal in quarantine
Target outside formula range
Insufficient inventory
Fallback formula used
```

Example:

```text
Warning:
"Current milk yield is outside the preferred target range
of the selected formula."
```

# 59. Recommendation Quality Control

Before official save:

```text
Validate animal
       ↓
Validate inputs
       ↓
Validate formula
       ↓
Validate ingredients
       ↓
Validate quantities
       ↓
Validate cost
       ↓
Validate nutrition
       ↓
Generate explanation
       ↓
Generate warnings
       ↓
Save
```

This prevents invalid recommendations from entering official history.

---

# 60. Animal Health and Recommendation

Health status can affect recommendation logic.

Example:

```text
healthStatus = Under Treatment
```

The recommendation engine may:

```text
Generate warning
```

or:

```text
Require expert review
```

depending on the approved feeding rules.

The FeedRecommendation model itself does not define the medical rule; it stores the recommendation context/output.

---

# 61. Pregnancy and Lactation

These are explicitly included in `inputSnapshot`.

Example:

```text
pregnancyStatus = true
lactationStatus = false
```

This allows the recommendation history to show exactly which reproductive condition was considered.

```text
        ↓
```

Saving/confirming recommendations may require stronger permissions depending on the final role-permission matrix.

Expert approval, if enabled:

```text

        ↓
expert_approved
```

# 66. Superseding Logic

When R2 replaces R1:

```text
R1.status = superseded
R2.status = confirmed
```

But only after R2 is successfully created.

Recommended transaction order:

```text
Create R2
   ↓
Validate R2
   ↓
Mark R1 superseded
   ↓
Commit
```

This avoids losing the old recommendation if creation of the new one fails.



Once confirmed:

```text

```

# 75. Edge Case — Formula Changes Before Confirmation

Preview generated using:

```text

```

Before confirmation:

```text
Formula v2.0 becomes active
```

The system should either:

```text
recalculate preview
```

or clearly show that the preview is based on the older formula.

For consistency, recalculating unconfirmed previews is preferable.

Once saved:

```text
Recommendation snapshot is fixed.
```

# 76. Edge Case — Ingredient Becomes Unavailable

If an ingredient becomes unavailable before confirmation:

```text

   ↓
Revalidate
   ↓
Warning / recalculate / alternative
```

The system should not save a recommendation that knowingly recommends an unavailable ingredient without an explicit business exception.

# 77. Edge Case — Animal Is Sold

If an animal is sold:


No new routine recommendation should normally be generated for that animal.

# 78. Edge Case — No Milk Data

For a non-lactating animal:


or an appropriate null/absent representation according to implementation.

The recommendation engine should not incorrectly interpret missing data as high production.

For lactating animals, missing milk data should generate an appropriate warning or require input.

# 81. Defense Questions

### Q: Why do you need FeedRecommendation if FeedFormula already exists?

**Answer:**

> "FeedFormula is reusable rule/template data, while FeedRecommendation is the animal-specific result generated at a particular time. The recommendation stores the animal's input snapshot and output so historical recommendations remain traceable."

---

### Q: Why are you storing the inputSnapshot?

**Answer:**

> "Because the Animal's current values can change. The snapshot preserves the exact inputs used when the recommendation was generated, which is essential for auditability, expert validation and thesis evaluation."

---

### Q: Why not just calculate old recommendations again from Animal?

**Answer:**

> "Because the Animal's current state and the feeding rules may have changed. Recalculation could make an old recommendation appear different from what the system actually recommended at that time."

---

### Q: Why don't you overwrite an old recommendation?

**Answer:**

> "Because recommendations are historical decision records. When a recommendation changes, we create a new record and mark the previous one as superseded."

---

### Q: Why is formulaId optional?

**Answer:**

> "A recommendation can normally be generated from a FeedFormula, but the architecture also allows future rule-engine or expert-generated recommendations that may not originate from one predefined formula."

---

### Q: Why store ingredientName when ingredientId already exists?

**Answer:**

> "ingredientId provides the reference identity, while ingredientName preserves the human-readable value shown when the recommendation was generated. This helps maintain historical readability if the master ingredient name changes."

---

### Q: Why store estimatedCost in the recommendation?

**Answer:**

> "Because ingredient prices change. The recommendation must preserve the estimated cost at the time it was generated instead of recalculating the historical cost using current prices."

---

### Q: What is the purpose of ruleVersion?

**Answer:**

> "It identifies the exact feeding-rule version used to generate the recommendation. This allows us to reproduce, compare and evaluate recommendations across different rule versions."

---

### Q: Does every preview need to be stored?

**Answer:**

> "No. Preview calculations do not need to be persisted. Once the user confirms the recommendation or it becomes officially generated, we save it as a historical FeedRecommendation record."

---

### Q: Why do you have `superseded`?

**Answer:**

> "It allows us to identify that an older recommendation has been replaced by a newer one without deleting the historical record."
