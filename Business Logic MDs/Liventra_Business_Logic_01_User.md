# 2. Purpose

The `User` model represents a person who has an account in Liventra.

It is the root identity record used for:

- Authentication
- Login/logout
- User profile management
- Farm membership
- System-level authorization
- Audit tracking
- Notification ownership
- Record creation/update attribution

A user is **not automatically a member of a farm**.

Farm-specific access is determined through the `FarmMember` model.

---

# 3. Why This Model Exists

Liventrа needs to distinguish between:

```text
Who is the person?
        ↓
User
```

and:

```text
What can that person do inside a particular farm?
        ↓
FarmMember
```

Example:

```text
User
Nabil
    |
    +---- Farm A → Owner
    |
    +---- Farm B → Worker
```

Therefore, `systemRole` and `FarmMember.role` have different responsibilities.

### User.systemRole

Controls **system-level authority**.

### FarmMember.role

Controls **farm-level authority**.

This distinction is important for multi-farm support.

# 5.6 `password`

### Type
String

### Required
Yes

### Stored Value

Hashed password only.

### Example

```text
$2b$12$...
```

### Purpose

Authentication credential.

### Critical Security Rule

The original password must **never** be stored.

Flow:

```text
User enters password
        ↓
Password hashing
        ↓
Hash stored in MongoDB
```

During login:

```text
Entered Password
        ↓
Compare with stored hash
        ↓
Match?
   ↙       ↘
 Yes       No
 ↓          ↓
Login     Reject
```

### Password Hashing

Use a secure password hashing mechanism such as bcrypt/Argon2 at implementation time.

### Important Rule

Password must never appear in:

- API response
- AuditLog `oldData`
- AuditLog `newData`
- Console logs
- Error logs

# 6. User vs FarmMember — Critical Business Logic

This is one of the most important concepts in Liventra.

## User

Answers:

> "Who is this person?"

## FarmMember

Answers:

> "What is this person's role in this particular farm?"

Example:

```text
User
Rahim
systemRole = user
        |
        +----------------------+
        |                      |
        ▼                      ▼
Farm A                    Farm B
Owner                     Worker
```

Therefore, backend authorization should never simply check:

```text
user.role
```

for farm operations.

It should resolve:

```text
Authenticated User
        ↓
Requested Farm
        ↓
FarmMember
        ↓
FarmMember.role
        ↓
Permission
```

# 8. Login Business Workflow

```text

     ↓
Find User by email/phone
     ↓
Check isDeleted
     ↓
Check isActive
     ↓
Compare password hash
     ↓
Valid?
  ↙     ↘
No       Yes
↓         ↓
Reject    Update lastLogin
          ↓
          Issue authentication token/session
          ↓

```

### On Failed Login

- Do not update `lastLogin`.
- Record security-relevant activity through the audit/security mechanism.
- Return a safe authentication error without revealing whether the email or password specifically was wrong.

# 15. Farm Membership Business Logic

User creation does **not** automatically mean farm access.

Example:

```text
User created
        ↓
No FarmMember yet
        ↓
No farm access
```

When the user joins a farm:

```text
Farm
  +
User
  ↓
FarmMember
  ↓
role assigned
```

This prevents unauthorized access to farms.

---

# 16. Authorization Flow

Every protected farm API should conceptually follow:

```text
Request
  ↓
Authenticate User
  ↓
Identify userId
  ↓
Identify requested farmId
  ↓
Find FarmMember
  ↓
Check isActive
  ↓
Resolve FarmMember.role
  ↓
Check permission
  ↓
Allow / Reject
```

Example:

```text
GET /api/farms/FARM-000001/animals
```

Backend should verify:

```text
Authenticated User
        ↓
Member of FARM-000001?
        ↓
FarmMember.isActive?
        ↓
Role allowed to read animals?
        ↓
Return only FARM-000001 data
```

This directly supports the SRS requirement that users must not access another farm's data. The SRS also specifies role-based access on protected routes. fileciteturn3file6

# 17. Data Isolation Rule

This is a **critical system-wide rule**.

A User must never access another farm's records simply by changing a URL parameter.

Bad:

```text
GET /animals?farmId=anotherFarm
```

and returning data without membership validation.

Correct:

```text
JWT/User Identity
      ↓
FarmMember lookup
      ↓
Authorized farm?
      ↓
Query scoped to farmId
```

Every farm-scoped service must enforce this.

Users may read their own profile.

Admins/superAdmins may have broader access according to system permissions.

Users may update allowed profile fields.

Sensitive fields require special workflow:

```text

isActive
isDeleted
```

These should not be treated as ordinary profile edits.

## Delete

Do not hard-delete normal user records.

Use:


# 23. Important Edge Cases

## Case 1 — User belongs to multiple farms

Allowed.

```text
User
 ├── Farm A → Owner
 ├── Farm B → Manager
 └── Farm C → Worker
```

---

## Case 2 — User is deactivated

```text
isActive = false
```

The user should lose active access, but historical records remain.

---

## Case 3 — User is soft deleted

```text
isDeleted = true
```

Historical data remains intact.

---

## Case 4 — Email changed

Old email should not automatically become the verified new email.

The new email should go through the appropriate verification flow.

---

## Case 5 — Phone changed

Same principle applies to phone verification.

---

## Case 6 — User is removed from a farm

Do **not** delete the User.

Only the corresponding:

```text
FarmMember.isActive
```

should be changed according to the membership workflow.

This preserves the user's other farm memberships and system identity.

# 27. Important Security Rules

### Rule 1
Never store plaintext password.

### Rule 2
Never return password hash in normal API responses.

### Rule 3
Never store password in AuditLog.

### Rule 4
Never trust `farmId` from the client without membership validation.

### Rule 5
Never trust `systemRole` sent by the frontend.

### Rule 6
System role changes must be authorized server-side.

### Rule 7
Deactivated/deleted users cannot authenticate.

### Rule 8
Historical references must remain valid after soft deletion.

# 29. Transaction / Consistency Considerations

User creation itself is relatively simple.

However, farm onboarding may involve multiple records:

```text
Create User
    ↓
Create Farm
    ↓
Create FarmMember
```

If one workflow creates multiple dependent records, the backend can use a MongoDB transaction where appropriate so the system does not end up with a partially completed onboarding process.

Example failure:

```text
User Created
   ↓
Farm Created
   ↓
FarmMember Creation Failed
```

This should be handled deliberately rather than leaving inconsistent onboarding state.

# 33. Defense Explanation

If your supervisor asks:

> **"Why did you create both User and FarmMember?"**

A strong answer is:

> "`User` represents the global identity of a person, while `FarmMember` represents that person's membership and role within a particular farm. This allows the same user to belong to multiple farms with different roles, while keeping authentication and farm-level authorization separate."

If asked:

> **"Why don't you store the farm role in User?"**

Answer:

> "Because a user can have different roles in different farms. Therefore, the role belongs to the User–Farm relationship, which is represented by FarmMember."

If asked:

> **"Why soft delete?"**

Answer:

> "Because Liventra contains historical operational records such as audit logs, treatment records, financial records and farm memberships. Hard deletion could break historical references, so account deletion is represented through a soft-delete state."
